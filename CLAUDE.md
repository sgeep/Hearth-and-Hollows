# Hearth & Hollows — Project Instructions for Claude

You are the lead gameplay programmer on **Hearth & Hollows** (working title; the repository, Unity project and code keep the technical name Hearthdelve), a 2D **top-down** fantasy life sim about owning and running a tavern and inn in the village of Kariaston, with nighttime delves into the Hollows, a top-down action roguelite dungeon beneath it, built in **Unity 6.6** (moving to **6.7 LTS** when it is released, and staying there through launch). The full design document is at `docs/GDD.md`. Read it before starting any new phase. This file records locked decisions and working rules; where it conflicts with the GDD, this file wins.

The game was a side-scroller through Phase 3. That prototype is preserved at the tag `v0-sidescroller-prototype`; the pivot to top-down happened on 2026-10-02 (see `docs/PROGRESS.md`, Phase 4). On 2026-10-04 the identity moved toward a Stardew-like village life sim centred on the tavern (GDD v0.5); the Stronghold direction was dropped.

## Making design decisions

The goal is the intended player experience, not systems that are merely correct. The full philosophy is in GDD §1.5 (design philosophy) and §6.5 (tavern immersion); these are the guardrails.

- **Experience first.** Before a non-trivial design choice, name the experience it should create and which parts of it are essential, then judge whether the mechanic produces that experience in play.
- **Lenses, not a checklist.** Jesse Schell's *The Art of Game Design* lenses are a shared vocabulary for questioning a design. Use the ones that fit the problem; no feature has to "pass" every lens, and "the book says so" is never the reason for a choice. (The book is reference material only: never commit or redistribute it.)
- **Playtesting beats theory.** For uncertain or expensive ideas: name the experience, build the smallest version that tests it, playtest, say specifically what felt good or bad and why, then iterate. Interpret player feedback; watch what players do, not only the fix they suggest.
- **When proposing an important design choice,** state the experience being targeted in a sentence and, where it helps, the lens or principle behind the recommendation.
- **Small, reversible choices inside an approved feature** can be made independently, in this order of concern: (1) the intended experience; (2) fun and clarity; (3) immersion where it strengthens that experience; (4) meaningful interaction over busywork; (5) meaningful choices and rich interactions over system count; (6) flow and pacing; (7) strong feedback for every player action; (8) elegant solutions that serve several purposes; (9) expose tuning values rather than treating first-pass balance as final; (10) confirm subjective calls in playtesting.
- **Immersion bias, with a flag.** Between two otherwise similar options, prefer the more immersive one. If the immersive option is clearly more repetitive, confusing, slow or frustrating, don't silently choose it for realism: flag the tradeoff.
- **Meaningful complexity over system count.** Before adding a rule or subsystem, ask whether it creates new decisions, interacts with existing systems, serves more than one purpose, strengthens the essential experience, and whether an existing system could do it more elegantly. Never add a feature just because another game has it.
- **Learning priorities (GDD §1.5).** The project is also deliberate practice in: dialogue writing, building and tavern customization, cooking minigames, funny and memorable NPC interactions, persistent relationships and reactivity, and top-down combat. In these areas depth, variety and iteration have value: don't pick the smaller of two viable options just because it's smaller, and large content sets (a big furnishing catalog, several cooking minigames, rich dialogue) are fine. Everything there must still earn its place. Spend complexity on these pillars before unrelated technical systems; combat should be good and satisfying but must not crowd out the others. The village life-sim direction strengthens all six.
- **Ask, don't guess,** on anything expensive to reverse, any major new mechanic or progression structure, and anything that conflicts with a locked decision.

## Locked design decisions

- **Names (2026-10-05, approved 2026-10-05; GDD §1.1, §2.1):** the game's working title is **Hearth & Hollows** (exactly that styling), replacing Hearthdelve and other title variants in player-facing and project-facing text. The underground world beneath Kariaston is **the Hollows**, its in-world proper name ("delve into the Hollows", "deeper in the Hollows", "the lower Hollows"); never "the Dungeons" or "the dungeon" as a place name. A run is a **delve**, the verb is **to delve**, and a **delver** is someone who does it, where it reads naturally. Biomes are regions at increasing depth within the one Hollows (the Cellars first, the Heart last), never separate dungeons. The three main places are Kariaston (the village), Tally Ho! (the player's tavern and inn) and the Hollows. **"Dungeon" stays the technical and genre term:** `Hearthdelve.*` namespaces and assemblies, `Dungeon*` classes, `Dungeon.unity`, `Dungeon_TestFloor`, the Dungeon input map, folders, asset paths, localization keys, save identifiers and the Unity Product Name are not renamed for branding; any such rename is its own planned migration.
- **Names, 2026-10-06 (owner's call; GDD Decided 35):** the tavern and inn is **Tally Ho!** (a name with its exclamation mark: "decorating Tally Ho!"), the village **Kariaston**, the head cook **Boog** (a goblin, he). They replace the Sunken Flagon, Brackenford and Gunta in player-facing text and docs; stable ids and asset names keep the old words (`gunta`, `brackenford_ale`, `Supply_BrackenfordMarket`, `Gunta.prefab`). Later the same day the server and bookkeeper became **Orik**, a dwarf with a ginger beard (he), replacing Pip (GDD Decided 43; stable id `pip`, `Pip.prefab` and `Staff_Pip.asset` keep their names). On 2026-10-07 Tally Ho!'s missing former proprietor became **Old Phi** (Phi'rai, a drow, once of the Fortunate Five; she), replacing Old Tamsin (GDD Decided 52–53; no stable id or save data ever named her).
- **Old Phi (owner's call; GDD Decided 52–53; the game's lines edited in the 4g closeout patch):** the tavern's former proprietor is **Phi'rai**, usually called **Old Phi**, a drow; she replaced Old Tamsin (who is not reintroduced in player-facing text or current canon; historical notes and records of earlier builds keep the old name). Once one of **the Fortunate Five** (her old adventuring party: history, texture, occasional anecdotes and future hooks, never the owner's tabletop campaign imported wholesale), she helped rebuild Tally Ho! with Orik, left for many years, came home decades later, took the tavern back and sought Orik out to hire him again; then she vanished into the Hollows. Orik's loyalty to her is a lifelong friend's. Let the history come out gradually (Orik, objects, later conversations), never as exposition in the opening.
- **Kariaston's founding (locked 2026-10-06; GDD §2.1, Decided 54):** long ago a source of evil opened beneath the region and caused a great war; Karias (Maximo's former apprentice, a great wizard) died sealing it, with Maximo among the sealers; the imperfect seal's seepage is the Hollows; Maximo founded Kariaston as a watch, named it for Karias, and will not (probably cannot; why is a future story decision) go back below. Kariaston exists because of the Hollows, and nearly every major character has their own relationship with them. Reveal it through people, places and partial stories, never a cosmology dump.
- **4h cast canon (locked 2026-10-06; GDD §2.10, Decided 55–58, 60):** Maximo keeps the Don Quixote personality, world figure the blue Knight on foot. Grim, a dwarf and former delver, found the infant Ogrin in the Hollows and raised him; Ogrin aged to about ten in a year or two, stopped, and is chronically ill; he calls him Grim, and the first "Dad" is a reserved later beat. Grim was one of the Fortunate Five (with Phi and Musashi); since 2026-10-07 **Musashi**, not Grim, keeps the market. Kaloren brings Ogrin herbs every third day (relief, no cure; not tied to his lichdom). Gimp is a half-elf hunter and ranger, nomadic and abrasive, standoffish to Bram, fond only of Boog and Phi, world figure `soldier_headband`. A framed drow portrait of Phi hangs in Tally Ho!. Ogrin keeps his own personality and agency; the illness and mystery never replace them.
- **Musashi (the owner's canon, 2026-10-07; GDD §2.10, Decided 61):** an elf who keeps the Kariaston market cart and stands by it; a friend of Phi, Grim and Orik, one of the Fortunate Five (Phi and Grim's party); a lifelong cook who lost his sense of taste to a curse from the Hollows and now sells ingredients so others can make good things he can't taste; his brother **Toshi** is missing in the Hollows (a quest to find him comes later; Toshi is only a name until then). Stable id `musashi`.
- **4h architecture (approved 2026-10-06; `docs/PLAN_4H.md` §0):** Kariaston is its own scene, loaded additively beside `Tavern.unity` in the daytime, doors a near-instant fade (locked unless the first architecture proof finds a serious problem). One source of truth for surface time (`SurfaceClock` in `GameState`, ticked by one Boot component; nothing else reads `Time.time` for the hour); 5 PM stops the clock and never starts Prep. Vigor caps strenuous daytime work only, refills on sleep, and is never spent by walking, talking, shopping, inspecting, decorating, Prep, service or the delve. The garden is four fixed beds with stable ids, a deliberate farming model whose rules stay plot-id based so a grid migration remains possible. NPC positions are derived from day + time + story, never saved. Kariaston's tilemaps are generated once and then hand-owned; tooling maintains named gameplay objects only. Pure rules in `Shared`; village behaviour in `Hearthdelve.Village`, which never depends on Dungeon.
- **Identity (2026-10-04, GDD §1.1):** *"Live in a strange fantasy village, grow and gather ingredients, run and personalize your tavern and inn, build relationships with villagers and visitors, and descend into the Hollows at night for things the surface world cannot provide."* The dungeon is a major pillar, but one activity inside a broader daily life.
- **The day (2026-10-04, GDD §3.1):** wake → free daytime → evening prep → tavern service (Prep → open → cook and serve → Results → close) → nighttime delve → return and sleep. Daytime becomes free roaming (decorating, the Inn, farming, ranching, fishing, villagers, quests, shopping, exploring), not a menu leading into the delve. Tavern → delve → sleep is fixed for now. Still open, never to be settled silently: a ticking clock versus player-controlled phases, and whether the delve can be skipped (GDD §13 Open 10). Since 4d step 5 the build runs this order, with a daytime placeholder (the old morning panel: storeroom, the delve meal, open for the evening) standing in for free daytime until the village milestone. A new game opens with the first night's delve (the storeroom starts empty).
- **Village and people (2026-10-04, GDD §2.8):** Kariaston is a small persistent village with a fixed authored cast of **named villagers** (mostly human; dwarves, elves, orcs, goblins, halflings, skeletons, liches and other folk are normal neighbours, not enemy archetypes). Tavern customers are named villagers plus generated **Visitors**. Most Visitors are transient and **never saved**; only a Visitor who becomes relevant (an Inn guest, a resident candidate) is promoted to a persistent identity. About **three fixed empty plots** (a target, not permanent) let settled Visitors become **recruited residents**: fixed sites, not city-building. Generated residents speak through authored modular dialogue and conditions, not procedural dialogue alone. Tone: a cozy fantasy community with odd people and occasional absurdity above the Hollows, a dangerous ancient underworld.
- **The keeper's room (the owner's call, 2026-10-07):** the upstairs room built as 4f's guest room is the keeper's own room for now (player-facing "your room"; stable id `guest_room` and its assets keep their names), and the hatch down to the Hollows is in its floor (Phi kept the way down where she slept). A later option lets the keeper move into a house of their own (direction, not scope); the Inn's guest rooms are still to come, on the same furniture architecture.
- **The Inn (GDD §6.8):** guest rooms use the **same** furniture, placement, customization and save architecture as the tavern; never a second decorating system. No numerical hotel-management rules are locked.
- **Ingredient sources (GDD §5.5):** the surface (farming, ranching, fishing, shops, villagers) provides dependable everyday ingredients; the Hollows provide monster, rare, magical and unusual ingredients, quest materials and discoveries. Farming never replaces the Hollows, and not every basic recipe needs an ingredient from the Hollows.
- **Stronghold direction dropped (2026-10-04):** no fortified Stronghold as the late-game home, no tower defense, no defense events. The property grows into a larger tavern, inn and home within the village. Story material that depended on it is kept and listed for revision (GDD §2.4, §2.9); don't build on it or delete it.
- **Tally Ho! and Kariaston as social places (4h requirement, recorded 2026-10-06):** in 4h Tally Ho! becomes a freely inhabitable home and social space in the daytime, not a sequence of management screens: the keeper wanders it, talks to whoever is there, sees Visitors and regulars, uses the room, decorates, walks between the tavern and a walkable Kariaston, and spends time there without the day advancing. The population is mixed fantasy folk, including selected friendly monsters; some authored creatures met in the Hollows may later progress *Hollows encounter → recurring visitor → Inn guest → possible Kariaston resident* (4h / Phase 5 direction; never arbitrary enemies, and nothing of it built in 4g). The character, dialogue and relationship architecture stays species-agnostic (`CharacterDefinition`, stand-ins and hubs by stable id), so an authored monster character needs content, not new systems.
- **Village life is direction, not scope:** farming, ranching, fishing, village free roam, Visitors, Inn guests and resident recruitment are built only in the milestones the roadmap gives them (GDD §11.1), never inside 4d.
- **Perspective:** top-down, in the spirit of Hades and Cult of the Lamb. 8-direction movement, dodge roll with i-frames, light combo plus heavy/charged attack. Aim by the mouse on keyboard and mouse (the system cursor stays visible) and by the right stick on gamepad, falling back to the movement direction while the stick is centred; the character faces where it aims (except while rolling, when it faces the roll), and attacks go that way (changed from movement-direction aim on gamepad after the 4e playtest, 2026-10-05). In the tavern the keeper likewise faces the mouse or the right stick (`PlayerLook`), except at stations and in menus, and faces their walk when the stick is centred. The dodge roll passes through enemies.
- **Art style:** pixel art from **Minifantasy** (8×8, top-down) by Krishna Palacio. Use URP 2D Renderer with the Pixel Perfect Camera. Reference resolution **320×180 at 8 PPU**, 1 world unit = 1 tile (8 px); **locked** after the 4a look test (2026-10-02). Point filtering, no compression on sprites. (This supersedes the side-scroller's 640×360 at 32 PPU.)
- **Lighting:** URP 2D lit sprites are the visual baseline. Every sprite and tilemap uses URP's lit sprite material (`Sprite-Lit-Default`), and each environment has an ambient (global) 2D light plus local lights: warm in the tavern, cooler and darker in the Hollows. Lighting must never cost gameplay readability. URP's 2D renderer allows only **one enabled global light per sorting layer**: when two places are loaded together (the tavern and Kariaston), each place's lights belong to its `Surface Area`, the inactive place's global light is authored disabled, and switching turns the old lights off before the new ones on.
- **Y-sorting:** custom transparency sort axis (0, 1, 0); sprite pivots at the feet; no gravity. Solid furniture and props block movement with a footprint that ends exactly at the bottom of their art (their sort point), so a character stopped in front of a piece always draws in front of it.
- **Animation:** our own SpriteSet path (`SpriteAnimationSet` assets shown by `CharacterSpriteAnimator`), deliberately instead of Mecanim Animator Controllers and clips. It is **presentation only**: TDE and our gameplay code stay authoritative for attack timing, damage, dodge and i-frames, and death; the animator only reflects that state and never drives gameplay.
- **Furniture catalogue (4f Checkpoint B):** pieces are added through the source table `Assets/_Project/Data/Furniture/Catalog/catalog.json` and the generator (*Hearthdelve → Generate → Furniture Catalog*, also run by the tavern updater), which copies only the named drawings into the repo; never hand-edit the generated definitions. Review with `Tools/furniture/contact.py`. Recolours use palette ramps taken from Minifantasy's own colourways, never free RGB tinting. A composite of Minifantasy drawings (the Larder Troll's tusks; Orik's look) is made by a script in `Tools/` from the raw packs, its output kept under `Tools/…/derived/` and read through a `derived:` source; record each in `docs/ASSET_MAP.md`.
- **Art files:** raw packs stay outside the repo in `C:\Dev\Minifantasy`. Import only what we need, into `Assets/ThirdParty/Minifantasy/<Pack>/`. Find art through the catalog CSVs first (name, category, biome tag) before browsing folders. For sheet-level catalog entries, inspect the sheet image and record what you find in `docs/ASSET_MAP.md` so the work isn't repeated; note there any gap that a pack we don't own appears to fill.
- **Named characters:** canonical story characters (Orik, Boog, Old Phi, Grukka, Sylvaris, Ser Aldric, and since 2026-10-07 Maximo, Kaloren Frosthand, Grim, Ogrin, Bart, Gimp and Glimmer; and Musashi and his brother Toshi; GDD §2.10) are not renameable; they may allow visual customization. Full naming and appearance customization is for hired or recruited workers (GDD §6.7). Renaming a canonical character is a story decision for the owner. Whether Visitors or recruited villagers can become staff is open (a possible cross-system interaction; don't lock it).
- **Protagonist:** customizable (name, body, colors). Minifantasy has no clothing or hair layers for attack animations, so customization is a pre-clothed body with **palette swaps** (skin, hair, outfit colors) rather than layered outfits. All bodies share one animation set so customization doesn't multiply animation work.
- **Essence (delve timer):** no calendar or deadline. Delves are limited by **Essence**, which drains over time in the Hollows and drops when the player takes damage. At zero Essence the player is forced out (treated as a death). Max Essence and drain rate are upgradeable in the tavern. The delve happens at night with **no separate time-of-night limit**: Essence is the only time pressure. Essence is the dungeon equivalent of Dave the Diver's oxygen. **Essence is the player's only health pool** — there is no separate HP. It is integrated with TDE's `Health` (a subclass backed by `EssenceMeter`), not run as a second system.
- **Safe ground (2026-10-06):** Essence doesn't drain in the rope room or the hole room at a floor's end (`FloorNode.PausesEssenceDrain`); damage still applies.
- **The surface (4h Checkpoint A, 2026-10-07; PLAN_4H H1, H3, H13, H15):** `Kariaston.unity` is its own scene, loaded additively beside `Tavern.unity` in the free daytime (`GameFlow` loads content sets; doors are instant fades, never scene loads); its world origin is (200, 0). The keeper wakes upstairs. Doorways (`AreaPassage`, `SurfaceDoor`) go through when the keeper is in the trigger and pushes the doorway's way (input or movement, even when blocked), never merely by standing in it, so arrivals can't bounce back (`Doorway`). Kariaston's tiles and dressing belong to the scene after its one-time generation; `SurfaceBuilder` (the tavern updater) maintains only `Kariaston/Gameplay` and the tavern's `Surface` objects. Pure surface rules live in `Shared/Surface`; the village's behaviours in `Hearthdelve.Village` (never Dungeon, never Pixel Crushers).
- **The surface clock (4h, locked):** one authority, `SurfaceTime` in Boot, advancing `GameState.Surface` by `Time.unscaledDeltaTime` capped per frame, never wall-clock time; 08:00 to the 17:00 cutoff (about 4 real minutes since the Checkpoint B playtest, while the day has little to fill it; tuned on `SurfaceClockConfig`). It stands still for conversations, `MenuPause` menus, transitions, `SurfacePause` holders (Decorate Mode, daytime panels, the Prep question), story scenes and lost focus. 5 PM stops it and closes the market and never forces Prep: evening prep begins only from the menu board, after the keeper confirms. Nothing else decides the hour.
- **Vigor and the garden (4h Checkpoint B):** Vigor is pure (`Shared/Surface/Vigor`): only what's been spent today is state, the day's maximum and every cost are tuning (`VigorConfig`: 6 a day, plant 2, tend 1, harvest 0 for the B playtest), refilled only in `DayRules.Sleep`. Work spends it at the level of a meaningful action (`VigorActivity`), all or nothing; a refusal changes nothing. The garden's rules are pure (`GardenRules`) over `GardenState` beds keyed by stable id (`garden_1`…); a bed never knows its shape (the scene's `GardenBed` shows it), so plots can become grid cells later. Growth happens once per new day inside `DayRules.Sleep` (each bed's `LastGrownDay`), in this order: freshness, the new day, growth, Vigor full, then the surface clock's morning (`GameFlow`). Harvests are ordinary storeroom stacks (Fine or Standard, fresh); there is no farm inventory and no provenance on stacks. Every garden action saves; so does beginning the evening (the day as it was left; the evening isn't a resume point).
- **Satchel:** 6 slots by default (upgradeable later). Identical parts (same ingredient, quality, and prep state) stack in one slot, up to 3 per slot by default (tunable in `DelveConfig`). When the satchel is full, picking up a new part opens a swap prompt.
- **Freshness:** stored per stack as a value from 0 to 1. When stacks merge, freshness is the count-weighted average. Stock is used least-fresh first; on a tie, lower quality first. Freshness drops in the satchel during a delve and in the storeroom overnight (both tunable in `FreshnessConfig`, built in 4c); preservation upgrades that slow it come later.
- **Death penalty:** on death (or Essence depletion) the player loses the entire haul except **one satchel slot they choose to keep — the whole stack in it** (the Lockbox, chosen on the death screen). Permanent unlocks, relics, gold already banked, and tavern progress are never lost. Unspent run currency is lost.
- **Runs:** room by room. Clear a room, doors unlock, choose the next room by its displayed reward. Floors are generated from a room graph, with a boss at the end of each biome.
- **Tavern:** a top-down room the player walks around. Customers path to tables; serving means carrying plates through the room. Minigames stay as screen panels. New areas unlock through story and upgrades; furniture and decor are placed freely inside them. No freeform construction yet, but don't design it out.
- **Tavern customization is a major pillar** (GDD §6.6, pillar 7; locked 2026-10-04): Tally Ho! becomes the player's own creation. Build it on data-driven furniture definitions and placed instances (never layouts baked into scenes, never duplicate scenes per layout), with functional furniture (stations, pass, tables, chairs, counters) in the same placement architecture where practical, nav rebuild plus validation against real service needs rather than arbitrary restrictions, and layouts saved through `SaveSystem`. Furnishings come from Gold, discoveries in the Hollows, bosses and story; use the Minifantasy collection extensively (a large curated catalog through the catalog CSVs, still importing only selected, usable sprites). One architecture for the whole property: tavern areas, Inn guest rooms, possibly the player's own quarters and later parts of the property. The open decisions in GDD §13 (placement model, editable walls, movable stations, ownership and duplicates, discovery death rules, boss trophy loss, palette technique, stat bonuses, decor's relationship effects) are prototyped or brought back, never settled silently.
- **Customization rules (4f plan, locked 2026-10-05; `docs/PLAN_4F.md` §22):** blocking furniture snaps to whole tiles with whole-tile footprints (pixel-exact bodies; decor may snap to quarter tiles), and holding the free-placement key (Shift / LB) places to the pixel, stored as the cell plus a nudge of under half a tile (amended at the owner's request after the Checkpoint A playtest); each piece has an explicit rotation mode (`None`, `AuthoredFacings`, `QuarterTurnSprite`: real 0/90/180/270° rotation that turns footprint, bodies, seat anchors, use points, surface anchors and lights together; pieces that would look wrong opt out individually); flipping is per-piece opt-in; owned copies, uniques capped at one, property-wide storage, removal never destroys; floor and wall finishes per area, structure fixed; stations movable (the Grill wall-bound, one of each); validation blocks only impossible service; recolouring remaps authored palette channels into cached textures and keeps `Sprite-Lit-Default`; no furniture stat bonuses in 4f. Curios are kept on extraction and lost on death; a boss trophy is granted when the boss falls and never lost. The seat upgrade is retired: seating comes from placed seats. `Tavern.unity` changes only through the idempotent in-place updater.
- **Special customer requests (4f Checkpoint D, 2026-10-06):** a request is an ordinary order a patron particularly wants tonight, never a quest or a second minigame: only a dish on today's menu that can be made at that moment, about one or two an evening (capped and seeded; tuned in `ServiceConfig`), met for a thank-you tip and a little Renown, missed for a frown and nothing worse. Requests live only for the evening and are never saved. Persistent and story quests are Quest Machine's.
- **Staff defaults (4f, 2026-10-06):** Boog (the cook, a goblin: the Goblin Sapper drawn as is; stable id `gunta`) starts off duty and is given a station at Prep (the player meets the cooking first); staff work is capped below a competent keeper's, so the player's best always beats it. Orik serves by default.
- **Balance changes go through the report:** after changing prices, dish values, staff caps or the economy settings, run *Hearthdelve → Balance → Evening Report* (`BalanceReport`, `EveningEstimate`) and keep `RenownAndBalanceTests` passing: market food is a safety net that never beats a delve night at the same skill.
- **Gameplay facts for 4g:** gameplay publishes what happened as stable-id events on the `EventBus` (`Shared/Game/GameFacts.cs`, plus `BossFirstCleared`). Add a fact when real gameplay produces it, never a dialogue-specific call; 4g's adapters listen there.
- **Save version:** 10 (since 4h Checkpoint B: the world's seed, the surface day's minute and Vigor spent, the garden's beds by stable id). A migration grants only what didn't exist when a save was made, exactly once. A version 7 save gets the opening marked done and the keeper's legacy name and look (Bram, the townsfolk); a version 8 save (4g Checkpoint A's playtests) is past creation, the opening and the prompts; a version 9 save gets a world seed derived from its own text (the same old file always gives the same seed until it's re-saved), the morning with Vigor full, and the starter beds empty. Nothing in the story is inferred from the day, bosses or furniture.
- **Rewards and the Satchel:** run, room, enemy and boss reward code must not assume rewards are only ingredients, Gold, Delve Marks, weapons or run power; persistent customization discoveries and **quest objects** are planned reward kinds, and ingredient rewards must not assume monster parts are the player's only ingredients. They never use Satchel slots: the Satchel is for ingredients only.
- **Tavern immersion is a design pillar** (GDD §1.3, §6.5). The player should feel they are running this tavern and cooking strange monster food: walking to stations, carrying plates, pouring, cooking, preparing ingredients, dealing with patrons and seeing parts become recognizable dishes. Immersion means capturing the essential experience, not simulating every mundane action, and it never licenses tedium. Later progression (staff, upgrades, mastery) may take over familiar low-level work while the player keeps the interesting steps.
- **Preparation depth:** everyday dishes stay quick; better dishes add one meaningful ingredient or process; rare and signature dishes may have several distinct stages (GDD §5.4). Every added step must earn its place (skill, choice, tactile fun, anticipation, risk/reward, feedback, perceived value, story or service logistics), never only add time. Recipe data must not assume that every dish is one station interaction forever, but this is long-term direction: it does not widen the current milestone's cooking scope.
- **Quests:** a persistent quest and objective system is a required feature, owned by Quest Machine (GDD §2.6). Ordinary service orders are not quests; they stay in the tavern service systems.
- **Relationships:** persistent relationships with selected named NPCs and recurring patrons are a required feature, whatever the middleware (GDD §2.7). Keep three things separate: **Renown** (the tavern's reputation), **Morale** (the village community, which produces Cheer; reinterpreted 2026-10-04, and whether it stays a separate measure is open) and **disposition** (what one character or faction thinks of Bram). Use relationship state selectively, where continuity creates value; Hearth & Hollows is not a dating or social sim.
- **Co-op:** none. Single-player only; do not build networking abstractions.
- **Story, dialogue and quests:** **Dialogue System for Unity** with **Quest Machine** (Pixel Crushers), presented through uGUI + Super Text Mesh, with portraits from the **Minifantasy Portrait Generator**, and **Love/Hate** (Pixel Crushers) as the relationship backend (approved 2026-10-06 with the 4g plan). Expose game state to the dialogue and quest systems through their Lua variables, custom functions and conditions, registered by Hearthdelve-owned adapters, rather than hard-coding story logic in C#. Locked 2026-10-03; it **replaces Yarn Spinner entirely** (no Yarn Spinner, and no second dialogue system alongside). Built in 4g.

## Tech stack

URP (2D Renderer), Input System (action maps: Dungeon, Tavern, Minigame, UI, and Decorate since 4f), Cinemachine, **TopDown Engine 5.0** (character controller, abilities, combat, enemy AI, camera, rooms), TDE's bundled **MMFeedbacks/MMTools** for all game feel, **Nice Vibrations** for haptics, **uGUI + Super Text Mesh** for all UI and player-facing text, sprite-sheet animation (SpriteSet, not Mecanim), Physics 2D (no gravity), Addressables, Localization, Dialogue System for Unity and Quest Machine (4g), Unity Test Framework.

- **TopDown Engine** replaces the custom kinematic character controller. We are not using Corgi Engine.
- **TDE knockback:** TDE's force knockback (`DamageOnTouch` AddForce, `TopDownController.Impact`) does nothing with our characters, because `TopDownController2D` moves the dynamic rigidbody with `MovePosition` every physics step. Enemy knockback is a short slide through `CharacterMovement` (`HitReaction`, `StaggerRules`); keep TDE's knockback type at NoKnockback.
- **TDE weapon aim:** melee weapons use `WeaponRotationSpeed = 0` (instant). TDE's default eases the weapon round, so attacks right after an aim change swing the old way.
- **Input:** the project uses the new Input System only, so use TDE's `InputSystemManager` (never the legacy `InputManager`). Our own action maps stay the source of truth: a subclass of `InputSystemManager` in our assembly maps the Dungeon and Tavern maps onto TDE's buttons; the Minigame, Decorate and UI maps don't go through TDE.
- **Cinemachine:** version 6.6.0, which TDE compiles against through its Cinemachine 3 code path (`MM_CINEMACHINE3`). Don't assume Cinemachine 2 namespaces.
- **Camera and scrolling:** **smooth scrolling**, locked on 2026-10-02 after comparing scroll modes in 4b. The Pixel Perfect Camera keeps the integer zoom for 320×180 at 8 PPU (crisp, evenly sized art pixels) but does **not** snap the view to the art-pixel grid (`gridSnapping = None`), so the camera and characters move in screen pixels and the world scrolls on every frame. Whole-art-pixel scrolling was tried first and rejected: at walking speed a diagonal moves the world on only about every other frame, in uneven 1.4 px jumps, which reads as judder. Cinemachine positions the camera and `CinemachinePixelPerfect` only corrects its size. The `CinemachineBrain` updates in **LateUpdate** (the player is an interpolated rigidbody), and the follow has **no damping**, so the player stays fixed on screen while it moves. The camera follows `PixelSnappedPresentation.Anchor`, which sits at the player's real position (its snapping is off; the look-test F4 comparison modes, pixel-perfect and half-pixel, turn it on). World-anchored UI (speech bubbles) is placed after Cinemachine from the camera the world is drawn from. VSync is on for every quality level. 2D lighting renders at screen resolution. `CameraFollowTests` guards this.
- **UI:** uGUI + Super Text Mesh + Minifantasy UI sprites replace UI Toolkit. STM does not work with UI Toolkit; use its **Ultra** shader under URP.
- **Font (locked 2026-10-03):** **Silver** (Poppy Works) is the body font for all player-facing text, and for dialogue (the 4g box draws it at 1×); one copy at `Assets/_Project/Fonts/silver/Silver.ttf` (it replaced m5x7, which is removed), adapted with plain single-pixel punctuation by `Tools/fonts/silver_plain_punctuation.py` (rerun it if the font is ever replaced). It is pixel-exact only at whole multiples of STM size 19 on the 320×180 grid, rasterised at 19, point filtered, on a 12-pixel line per multiple; UI canvases scale by whole pixels (`PixelCanvasScaler`). There is no clean size smaller than 19: never draw text under it.
- **Type scale (UI foundation pass, 2026-10-06):** every text has a style (`TextStyle`: **Display** 3×, **Heading** 2×, **Body**, **Secondary** and **Prompt** 1×), set by the builders (`LookTestBuilder.Text`/`DungeonUI.Title` with a `TextStyle`, never a size) and baked from the one asset `Data/UI/TypeScale.asset` by the updaters (`GameFonts.Apply`, `ApplyToOpenScene`); each text carries a `StyledText`. Secondary and Prompt share Body's metrics and differ by colour and placement. Headings are for screen titles and major state titles whose English leaves a fifth of their box spare; sub-panel titles stay 1×. A button's label keeps two pixels clear of its frame. `TypographyTests` check every text against the scale and every fixed English string against its box. A decorative title font may be chosen in the menus and polish milestone (4i); don't add one before.
- **Glyph coverage:** every string in every locale must be drawable in Silver; `TextStyleTests` checks the tables against the font itself. Silver covers Latin, Greek, Cyrillic, Japanese, Chinese, Korean, Thai and more (not Arabic or Hebrew). There is no fallback font, deliberately (the web build has no system fonts): a language Silver can't draw needs a font decision, not a quiet fallback.
- **Localization:** every player-facing string goes through a Localization string table — no literal UI text in C# or in prefabs. Use Localization 1.5.13 or later (1.5.8 does not compile on Unity 6.6).
- **English text style (locked 2026-10-03):** player-facing English is written in lower case; genuine proper nouns keep their capitals (Bram, Orik, Boog, Kariaston, Tally Ho!, Ser Aldric Vane, the Hollows, the Cellars, the Larder Troll, Hearth & Hollows), and so do the game's **resource names** (Essence, Renown, Morale, Cheer, Delve Marks; only when the word means the resource) and control labels (E, Space, A, LB, WASD). **Gold is the exception: always lower case in player-facing text** ("12 gold", "gold earned"; changed 2026-10-05); design docs may still write Gold for clarity. Recipes, ingredients, statuses, system names, upgrades and menu commands are not capitalised unless deliberately a proper noun. Player-facing English uses **American spelling** (color, catalog, gray, harbor, traveling, paneling; owner's call, 2026-10-05; `TextStyleTests` checks it); code identifiers, ids and docs may keep British forms. This is a writing rule: the casing is authored in the source strings, never applied in code (no `ToLower`, no STM casing), and other languages follow their own conventions. Ask when a case is ambiguous.
- **Addressables:** deferred. Do not use Addressables for game content until we build biome/room loading. (The package is present only as a transitive dependency of Localization, which stores its string tables in Addressables groups; leave those Localization-managed groups alone and don't add our own yet.)
- **Pixel Crushers (since 4g Checkpoint A):** Dialogue System for Unity 2.2.74, Quest Machine 1.2.74 and Love/Hate 1.10.74.1, imported by the owner into `Assets/Plugins/Pixel Crushers` (one Common), compiled through their own assembly-definition packages (`PixelCrushers` ← `LoveHate` ← `DialogueSystem` ← `QuestMachine`); no demos (`docs/THIRD_PARTY.md`). Never modify their code; never reimport them wholesale (add only a missing official support package).
- **Story architecture (4g):** gameplay → facts (`EventBus`) → `Hearthdelve.Story` adapters → Pixel Crushers. `Hearthdelve.Story` and `Hearthdelve.Story.Presentation` are the only runtime assemblies that reference Pixel Crushers (the Story editor assembly builds content); Dungeon, Tavern, Shared, Core and UI never do, and reach the story only through `StoryServices` (`IStoryStateParticipant`, `IConversationService`) and facts. The `StoryHost` in Boot owns the Dialogue Manager, Quest Machine and the Love/Hate faction manager, and keeps a **social stand-in** (a Love/Hate faction member keyed by stable character id, independent of any visible NPC) per tracked character, so deeds reach characters across scenes. Conversations ask about the game only through `HH_` Lua functions (`HH_Affinity`, `HH_Respect`, `HH_Remembers`, `HH_QuestState`, `HH_GiveQuest`, `HH_PlayerName`, `HH_Day`, `HH_TimesDefeated`), never through Love/Hate's or Quest Machine's own Lua. Love/Hate memories age on the game's day clock (Pixel Crushers' `GameTime` in manual mode), never real or paused time.
- **Dialogue authoring (decision D1, 2026-10-06):** the Dialogue System's editor and database (`Data/Story/HearthDialogue.asset`) are authoritative for conversations; no text-file importer. `Hearthdelve → Story → Update Story Content` only gives new entries a `Guid` field and writes their English into the **Dialogue** string table (Unity Localization stays authoritative for player-facing text; dialogue is shown from the table, keyed by Guid). Quest text holds Localization keys; Quest Machine's text tables are not used. Read-only exports and review dumps may come later.
- **Accents (the owner's call, 2026-10-07):** dwarves (Orik, Grim, any dwarf) speak with a **Scots** accent, **Bart** with a **southern Texas** one, **Musashi** with a **thick Japanese** one; everyone else plainly for now. Accents are written into the English lines (like the lower case; never applied in code, so other languages carry voice their own way), and carried by word choice, rhythm and grammar rather than phonetic misspelling: Scots "aye", "wee", "ken", "cannae", "dinnae", "tae", "no'"; Texas "y'all", "reckon", "fixin' to", "darlin'"; Musashi clipped and formal ("i am", "i cannot"), articles dropped, the odd Japanese word ("hai", "ohayo", "onegai", "-san" for the keeper), never swapped letters. Applied to Orik's and Musashi's lines on 2026-10-07 (a one-off author's edit); on lines the owner wrote, only the accent changes, never their wording.
- **Editing authored dialogue from code (4g Checkpoint C):** a change to a conversation that already exists is an author's edit, made once and only where the entry is still exactly as written (anything the owner changed is left alone), never a builder step that reruns. The owner's node-editor workflow is approved and canonical.
- **The tooling never rewrites a conversation (4g Checkpoint B):** first drafts are seeded once, as ordinary conversations, entries and links, and logged in `Data/Story/DialogueSeeds.txt`; a logged title is never written again, whether it's been edited, renamed or deleted in the node editor (delete its line to seed it afresh). Branching, conditions and scripts live in the graph; C# decides only *when* a conversation plays (`OpeningRules`) and what the `HH_` functions answer. Quest Machine quests and deeds the builder makes are created once and then tuned on their assets.
- **The keeper (4g Checkpoint B):** four bodies (townsfolk, the Amazon as "warrior", the Yellow Beard dwarf, the Wild Orc), each a complete Minifantasy figure with every animation the keeper plays; skin, hair and clothes recoloured by the furniture recolour from ramps sampled from Minifantasy's own art (`Data/Characters/Keeper`, built by `KeeperContent`), never tinted; a name of up to 16 letters. A new game goes New Game → the creator → arrival day.
- **Relationship reactivity (4g Checkpoint C):** a compact deed vocabulary (`displayed_trophy`, `returned_boogs_bomb`, `felled_larder_troll`, `kept_a_wish`, `fine_butchery`), each from an existing gameplay fact and only when remarkable (a boss's first fall, a request met at quality 0.9+, the keeper's own butchery at 0.9+: `RelationshipRules.Qualifies`); never every event. Characters read the same deed through their own values (Boog: nerve and craft; Orik: warmth and craft, not nerve). Repeats fade 1, ½, ¼, ⅒, then nothing (`RepeatFactor`, applied as Love/Hate's acclimatization curve on the stand-ins). Relationship change is felt through dialogue, never shown as numbers. Each character's conversation is a hub (`Boog/Hub`, `Orik/Hub`) in priority order: critical story and quest → one-time relationship callbacks → their everyday Talk conversation. Conditions stay few (a seeded day rule, a day, the opening, a quest object); dialogue keeps its own. ## Game feel

- Feedback is part of immersion, not decoration: it should tell the player how well they did and how it felt at the same time, so a good chop, pour or plate reads in the moment, not only as a score afterwards (GDD §6.5).
- Every new player-facing interaction gets a **feedback pass** covering visuals, sound and haptics, authored together in the same `MMF_Player` so each important moment has one combined feedback.
- Haptics use **named patterns** from the haptic library (ScriptableObjects). Gameplay triggers named patterns, never raw motor values. Any mapping from a gameplay value to intensity (e.g. pour speed → rumble strength) is pure logic with EditMode tests.
- All feedback intensities respect the player's settings (screen shake, flash, vibration on/off, vibration intensity, reduced-intensity accessibility option). Haptics degrade gracefully where unsupported.
- Game feel matters most. Expose tuning values (dodge i-frames, combo windows, hit-stop duration, Essence drain) in ScriptableObjects so I can tweak them in the editor without code changes.

## Architecture rules

- Data-driven: gameplay content is ScriptableObjects (`IngredientDefinition`, `RecipeDefinition`, `EnemyDefinition`, `WeaponDefinition`, `CustomerProfile`, `BiomeDefinition`, `RoomDefinition`, `TavernUpgradeDefinition`). No balance numbers hard-coded in MonoBehaviours.
- Systems communicate through event channels or a lightweight event bus, not direct references across the Dungeon/Tavern boundary.
- **TDE boundary:** bridge TDE/MoreMountains events to our `EventBus` at the boundary instead of spreading `MMEventManager` through our systems.
- **UI layering:** `Hearthdelve.UI` may read gameplay state from `Hearthdelve.Tavern` and `Hearthdelve.Dungeon` directly (e.g. live minigame meters). Gameplay assemblies never reference UI; they publish events or expose read-only state.
- Assembly definitions: `Hearthdelve.Core`, `Hearthdelve.Dungeon`, `Hearthdelve.Tavern`, `Hearthdelve.Shared`, `Hearthdelve.UI`, `Hearthdelve.Story`, `Hearthdelve.Story.Presentation`, `Hearthdelve.Editor`, `Hearthdelve.Story.Editor`, `Hearthdelve.Tests`. Dungeon and Tavern must not reference each other; they share through Core/Shared. Only the Story assemblies reference Pixel Crushers (`StoryTests` checks).
- Pure logic (damage calculation, harvest rules, recipe scoring, economy, Essence drain, pathfinding, haptic intensity mapping, save serialization) lives in plain C# classes with EditMode unit tests. MonoBehaviours stay thin. TDE-dependent behaviour gets PlayMode tests.
- Minigames implement a common `IMinigame` interface (Begin, Tick, Evaluate returning a 0–1 score) so staff can auto-resolve any station.
- **Pixel Crushers boundary:** Dialogue System, Quest Machine and Love/Hate are reached only through Hearthdelve-owned adapters and bridges, at the `EventBus` boundary. Gameplay systems publish gameplay events (an ingredient harvested, a dish served, a boss killed); the adapters turn them into quest progress, dialogue variables or relationship changes. No Pixel Crushers calls inside Dungeon, Tavern, combat, inventory or other gameplay code, pure logic never depends on Pixel Crushers packages, and Dungeon and Tavern still never reference each other.
- Save data is versioned JSON. Autosave at the day's safe boundaries: after the evening (before the delve), as soon as the delve ends, after each upgrade, and on sleeping; never mid-run. Transient Visitors are never saved. **`SaveSystem` is the only authoritative save.** Dialogue, quest and relationship state are captured and restored by adapters inside its save/load lifecycle, never through a separate player-save path.

## Working in Unity from outside the editor

- Prefer writing **Editor scripts** (menu items under `Hearthdelve/…`) that generate prefabs, ScriptableObject assets, and scenes, instead of hand-editing `.unity`, `.prefab`, or `.asset` YAML. Hand-edit YAML only for small, well-understood changes.
- Never hand-write or modify `.meta` files or GUIDs; let Unity generate them. (Copying a file together with its existing `.meta` when porting from `Hearthdelve-v0` is fine and keeps asset references intact.)
- **Scenes are never overwritten without asking.** Generators may create a scene that doesn't exist, but must not overwrite an existing scene unless I've explicitly approved it for that run (in the editor they show a confirmation dialog; in batch mode, don't pass `-rebuildScene` without my go-ahead). If a generator change needs a scene rebuild, ask first, or add the new objects to the existing scene instead.
- When Unity is available on the command line, verify work by running batch mode compiles and tests (EditMode and PlayMode via `-runTests`). Report failures honestly; don't claim something works without running it.
- Use real Minifantasy art where it exists. Where it doesn't (including all sound, for now), use placeholders and name them clearly (`PH_…`) so they're easy to replace.
- Some things need me in the editor (playtesting feel, wiring references a script can't set, controller rumble checks). When you hit one, give me short numbered steps and continue with whatever doesn't depend on it.
